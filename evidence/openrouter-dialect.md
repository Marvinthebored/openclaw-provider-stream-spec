## 2. Frame inventory

OpenRouter's `/api/v1/chat/completions` with `stream: true` emits a sequence of `text/event-stream` lines. Every "frame" is a `data: {...}` line whose JSON has `object: "chat.completion.chunk"`, plus interleaved SSE comment lines and a terminal `data: [DONE]`.

| Frame/event type | Key fields | Semantics | Source (docs § / capture file) |
|---|---|---|---|
| **Chunk frame** (`data: {...}`, `object: "chat.completion.chunk"`) | `id`, `object`, `created`, `model`, `choices[]` | Standard OpenAI-CC-compatible streamed chunk. One or more per turn. | streaming ref |
| `choices[].delta.content` | string | Incremental visible assistant text (final-answer lane). | streaming ref |
| `choices[].delta.reasoning` | string | Incremental plaintext reasoning/thinking text (legacy/simple lane; alias `reasoning_content` also seen on some provider passthroughs). | reasoning-tokens guide |
| `choices[].delta.reasoning_details[]` | array of typed objects (`reasoning.text`, `reasoning.summary`, `reasoning.encrypted`) | Incremental, *structured* reasoning blocks — the richer, provider-faithful lane that supersedes plain `reasoning` for round-tripping. | reasoning-tokens guide |
| `choices[].delta.tool_calls[]` | `index`, `id`, `type: "function"`, `function.name`, `function.arguments` (partial JSON string fragments) | Incremental tool-call construction. First chunk for a given `index` carries `id`+`function.name`; subsequent chunks for the same `index` carry only `function.arguments` fragments to be concatenated. | tool-calling guide, OpenAI-CC streaming convention |

Not part of the OpenAI-CC schema; opt-in only. | chat-completion ref |

## 3. Content lanes

- **Final answer text**: `choices[].delta.content` (streaming, incremental string) / `choices[].message.content` (non-streaming, string or content-parts array, or `null` when the turn is pure tool-calls). This is the only lane mapped to `final_answer`.

- **Thinking/reasoning (incl. signed/redacted/summary variants)**: Two parallel lanes that OpenRouter populates simultaneously when the upstream model supports it:
  - `reasoning` (string, both `message.reasoning` and `delta.reasoning`) — a flattened plaintext concatenation, aliased as `reasoning_content` by some passthroughs (DeepSeek-style). Convenient but lossy: loses block boundaries, signatures, encryption.
  - `reasoning_details[]` (array, both `message.reasoning_details` and `delta.reasoning_details`) — structured, provider-faithful blocks. Three documented `type` variants:
    - `reasoning.text` — `{ type: "reasoning.text", text, signature?, id?, format, index? }`. `signature` carries provider cryptographic signatures (e.g. Anthropic's thinking-block signature) when present.
    - `reasoning.summary` — `{ type: "reasoning.summary", summary, id?, format, index? }`. Used for OpenAI-style reasoning summaries (the model's hidden chain-of-thought is not exposed; only a model-generated summary is).
    - `reasoning.encrypted` — `{ type: "reasoning.encrypted", data, id?, format, index? }`. `data` is opaque (e.g. base64) provider-encrypted reasoning state (OpenAI Responses-style `encrypted_content`, or Anthropic `redacted_thinking`), round-trippable but not human-readable. In streaming, may render as `[REDACTED]` placeholder text while the real payload arrives in `data`.
    - Common fields: `id` (string|null), `format` (provider-tag string: `"anthropic-claude-v1"`, `"openai-responses-v1"`, `"google-gemini-v1"`, `"xai-responses-v1"`, and presumably a deepseek-tagged format for R1), `index` (position for reassembly when multiple reasoning blocks/segments interleave).

- **Narration/commentary/preamble**: Not a distinct OpenRouter lane. Interim assistant text between tool calls (when a model emits prose, then a tool call, then more prose) shows up as additional `delta.content` chunks before/after `delta.tool_calls` chunks within the same `choices[0]` stream — there is no separate channel/type tag distinguishing "narration" from "final answer" the way Harmony's `commentary`/`final` channels do. A consumer must infer phase from position relative to `tool_calls` and `finish_reason`.

- **Tool calls + results**: `delta.tool_calls[]` (streaming) / `message.tool_calls[]` (final), each `{ id, type: "function", function: { name, arguments } }`. Streaming chunks are keyed by `index` for parallel-tool-call assembly: the first chunk for an index carries `id` + `function.name` (+ empty/`""` `arguments`), subsequent chunks for the same `index` carry only `function.arguments` fragments to be string-concatenated into a full JSON document. `finish_reason: "tool_calls"` signals the turn ended because the model wants tool execution. Tool **results** are not part of the streamed-out shape — they go back in as `role: "tool"` messages in the *next* request; OpenRouter doesn't emit a "result" frame itself.

- **Usage/metadata**: `usage` object on the final chunk (only with `stream_options.include_usage: true`) — `prompt_tokens`, `completion_tokens`, `total_tokens`, `cost` (USD, OpenRouter-side), `cost_details.upstream_inference_cost`, `is_byok`, `prompt_tokens_details.{cached_tokens, cache_write_tokens, audio_tokens, video_tokens}`, `completion_tokens_details.{reasoning_tokens, audio_tokens, accepted_prediction_tokens, rejected_prediction_tokens}`. Optional `openrouter_metadata` (requires opt-in header) carries routing/provider-selection metadata.

- **Errors**: Pre-stream errors are a non-streaming JSON `{error: {code, message, metadata?}}` with HTTP status = `code`. Mid-stream errors are SSE frames shaped like a normal chunk but with a top-level `error` key, `delta.content: ""`, `finish_reason: "error"`, and optional `native_finish_reason` carrying the upstream provider's own error/stop string. HTTP status remains 200 for mid-stream errors since headers were already sent.

## 4. Ordering & interleaving guarantees

- Frames for a single `choices[0]` arrive in emission order; `index` fields (on `tool_calls` and `reasoning_details`) are the authoritative reassembly key, not arrival order alone, because some providers may emit reasoning and content/tool-call deltas in bursts.
- Documented ordering intent: reasoning (`reasoning` / `reasoning_details`) precedes the final `content` for a given segment — i.e., a model "thinks" then "answers" — but OpenRouter does not document a hard guarantee that all `reasoning_details` chunks complete before the first `content` delta for every provider; some providers interleave (e.g., emit a reasoning summary, then content, then more reasoning before a tool call). Treat ordering as "mostly sequential per logical block, but block boundaries are provider-dependent."
- `delta.content` and `delta.tool_calls` can both appear across the lifetime of a single `choices[0]` stream (prose → tool call → more prose is possible for models that support it), but OpenRouter's docs don't define a channel tag to separate "narration before tool call" from "final answer after tool call" — both are just more `delta.content` chunks. A consumer must use `finish_reason`/turn boundaries (i.e., a new request after tool execution) to know whether trailing content is truly final.
- `reasoning_details[].index` provides ordering/identity *within* the reasoning-details array for a single message; it is not a global sequence number across the whole SSE stream.
- SSE keepalive comment lines (`:`-prefixed) can appear interleaved between any two `data:` lines, including mid-reasoning-block, and carry no ordering information of their own — they must be skipped, not counted as frames.

## 5. Delta vs snapshot semantics

- `delta.content`, `delta.reasoning`, `delta.tool_calls[].function.arguments` are all **incremental** (concatenate across chunks).
- `delta.reasoning_details[]` is documented as appearing "incrementally in delta chunks as reasoning generates" — but it is an *array* of objects, each themselves potentially partial. The doc-sourced model is: each `reasoning_details` entry is identified by `(type, index, id)`, and the `text`/`summary`/`data` field of an entry with a given identity is incrementally extended across chunks (concatenation), the same way `delta.content` is. OpenRouter does not document whole-object replacement ("snapshot") semantics for `reasoning_details` — assume append/concatenate-by-identity, but this is a **prime candidate for capture verification** (see §7).
- `delta.tool_calls[]` first-chunk vs subsequent-chunk shape is the standard OpenAI-CC convention: first chunk per `index` = snapshot of `id`+`type`+`function.name` (with `arguments` empty or absent), later chunks per same `index` = pure `arguments` deltas to concatenate.
- The final `usage` chunk is a one-shot **snapshot** (full totals), not incremental — it is not meaningful to "sum" usage chunks because there is normally only one.
- `choices[].message` (non-streaming) is always a full snapshot — not applicable to the streaming path but relevant if a consumer falls back to `stream: false`.

## 6. Termination & final-frame semantics

- Normal termination: the last `chat.completion.chunk` for a choice carries a non-null `finish_reason` (`"stop"`, `"length"`, `"tool_calls"`, `"content_filter"`) and typically `native_finish_reason` (upstream-specific string, unnormalized).
- If `stream_options.include_usage: true`, **one additional chunk** follows the finish-reason chunk: a chunk whose `choices` is empty/absent and which carries only the `usage` object (and optionally `openrouter_metadata`). This usage-only chunk is the true last JSON frame.
- After the usage chunk (or after the finish-reason chunk if usage wasn't requested), the stream ends with the literal line `data: [DONE]`.
- Mid-stream error termination: a chunk with top-level `error`, `choices[0].delta.content: ""`, `finish_reason: "error"` appears in place of (not in addition to) the normal finish-reason chunk; it is unclear from docs whether `[DONE]` still follows an error frame — treat as **uncertain, needs capture verification**.
- "Final answer" is distinguished from reasoning/commentary purely by *field* (`content` vs `reasoning`/`reasoning_details`), not by a separate phase/channel marker — there is no OpenRouter-native equivalent of Harmony's `final` channel tag. A consumer must treat the *last* contiguous run of `delta.content` before `finish_reason` as the final answer, but cannot structurally distinguish "answer so far" from "the answer" before the finish-reason chunk arrives.

## 7. Observed dialect deviations

This is the core "aggregator with imperfect formatting" catalogue: what a consumer **cannot rely on** vs. talking to Anthropic, OpenAI, or DeepSeek natively. Items originally marked **[NEEDS CAPTURE]** have been updated with capture-verified findings from the three live SSE captures (claude-sonnet.sse, gpt-5-mini.sse, deepseek-r1.sse; all captured 2026-06-12). Remaining **[UNRESOLVED]** items lack coverage in the available captures.

1. **Two parallel, possibly-inconsistent reasoning lanes — CAPTURE VERIFIED.** All three models populate *both* `reasoning` (flat string) and `reasoning_details[]` (structured array) simultaneously in every reasoning chunk. They are mirror-copies of the same incremental text fragment within each chunk: `reasoning` carries the same substring as `reasoning_details[0].text` (or `.summary`). **EXCEPTION confirmed for encrypted lane:** GPT-5-mini's final `reasoning.encrypted` chunk (gpt-5-mini.sse line 81) carries `reasoning: null` while `reasoning_details[0]` is `type: "reasoning.encrypted"` — proving `reasoning` is null/absent when the entry has no plaintext to flatten. The dual-lane is therefore: identical-mirror during text/summary chunks; `reasoning: null` during encrypted chunks. A dedup consumer keying on `reasoning` alone will lose the encrypted payload entirely.

2. **`format` is the only signal for upstream dialect — CAPTURE VERIFIED, with a surprise.** Confirmed `format: "anthropic-claude-v1"` (claude-sonnet.sse lines 13, 17, 21) and `format: "openai-responses-v1"` (gpt-5-mini.sse lines 5–81). DeepSeek R1 via OpenRouter/Novita emits `format: "unknown"` (deepseek-r1.sse, all 568 reasoning_details chunks), not a named DeepSeek format tag — the docs' promise of a DeepSeek-tagged format string does not hold in this capture. A consumer branching on `format` for DeepSeek must handle `"unknown"` as the actual value from this provider path.

3. **GPT-5-mini emits BOTH `reasoning.summary` and `reasoning.encrypted` — CAPTURE VERIFIED.** With `reasoning.effort: "low"`, OpenRouter's GPT-5-mini passthrough delivers 38 chunks of `type: "reasoning.summary"` (incremental display-safe summary text, format `openai-responses-v1`, gpt-5-mini.sse lines 5–79), followed by 1 chunk of `type: "reasoning.encrypted"` (opaque base64 blob, same `index: 0`, format `openai-responses-v1`, line 81). The two appear sequentially under the same `index: 0`, not as separate entries. Consumers must handle both types appearing for the same logical block. The doc's claim that "summaries are the default" and "encrypted is opt-in" is partially wrong: both arrive without any extra opt-in in this capture. `reasoning` mirrors summary fragments during the summary phase and is `null` in the encrypted chunk.

4. **`native_finish_reason` values confirmed per model — CAPTURE VERIFIED.** Claude Sonnet: `finish_reason: "stop"`, `native_finish_reason: "end_turn"` (claude-sonnet.sse lines 27, 29). GPT-5-mini: `finish_reason: "stop"`, `native_finish_reason: "completed"` (gpt-5-mini.sse lines 115, 117). DeepSeek R1 via Novita: `finish_reason: "stop"`, `native_finish_reason: "stop"` (deepseek-r1.sse last data lines). `native_finish_reason: "completed"` (GPT-5-mini/OpenAI) has no OpenAI-native Chat Completions equivalent; a consumer expecting only `"stop"/"length"/"tool_calls"` will miss it unless pattern-matching on the normalized `finish_reason` field.

5. **Keepalive text is exactly `: OPENROUTER PROCESSING` — CAPTURE VERIFIED.** All three models emit this exact string with no payload variation. Counts: claude-sonnet.sse 6 occurrences (lines 1–11, interleaved before first data chunk); gpt-5-mini.sse 2 occurrences (lines 1–3, before first data chunk); deepseek-r1.sse 5 occurrences (lines 1–9, all in the preamble before streaming begins). Placement: preamble-only in all three captures — no mid-stream keepalives observed after the first data chunk. The SSE parser needs only "any line starting with `:`" (not an exact match), but the text itself is stable across all three models. Frequency appears to correlate with upstream latency before first token.

6. **Mid-stream errors: [UNRESOLVED].** No error frames appear in any of the three captures (all completed normally). The `[DONE]`-after-error-frame question remains open.

7. **`reasoning_details[].index` reassembly: CAPTURE VERIFIED — single-index, stable, `index: 0` throughout.** All three models use `index: 0` for every `reasoning_details` chunk across the entire stream. No secondary indices appear (no multi-block interleaving observed in these captures). This means `(type, index)` keying is sufficient for single-block reassembly — but all reasoning fits one block per turn here, so multi-block behavior (e.g., `index: 1` for a second thinking block) is not tested. `id` field: absent in claude-sonnet.sse and deepseek-r1.sse `reasoning.text` chunks; present only in the gpt-5-mini.sse `reasoning.encrypted` chunk (`id: "rs_0def81a9493803c5016a2b65a8bd3081968e1f7de2d8c8f836"`). For single-block scenarios, `index` alone is the stable key; `id` cannot be relied upon across all models.

8. **No structural separation of narration vs. final answer** (vs., say, Harmony's `commentary`/`final` channels, or the Responses API's separate output-item types). Everything text-shaped that isn't reasoning is `delta.content`/`message.content`, full stop. Any "commentary vs. final_answer" distinction OpenClaw wants must be synthesized heuristically (position relative to `tool_calls`/`finish_reason`), which is strictly less information than upstream-native APIs that tag this explicitly. *Not impacted by captures (no tool calls in test prompts); status unchanged.*

9. **`provider` field leaks into base response without opt-in header — CAPTURE CONTRADICTS DOC.** All three captures include a top-level `"provider"` field in every chunk (e.g., `"provider":"Anthropic"`, `"provider":"OpenAI"`, `"provider":"Novita"`) without any `X-OpenRouter-Metadata` header being sent. This is not documented in the base schema but is present throughout. `"provider":"Novita"` (deepseek-r1.sse) identifies the actual upstream serving endpoint (a third-party Novita inference node, not DeepSeek directly), partially closing the §7.9 gap without the opt-in header. Consumers can read `provider` from any chunk for endpoint identity.

10. **Usage/cost chunk shape confirmed — CAPTURE VERIFIED.** All three models emit a usage-only final chunk immediately before `data: [DONE]`, containing `cost`, `cost_details.upstream_inference_cost`, `prompt_tokens_details`, `completion_tokens_details.reasoning_tokens`. `service_tier` field present on claude-sonnet.sse and gpt-5-mini.sse usage chunks (`"service_tier":"default"`); absent/null on deepseek-r1.sse (`"service_tier":null`). `completion_tokens_details.reasoning_tokens` correctly accounts for reasoning: Sonnet 13, GPT-5-mini 52, DeepSeek R1 1028. Two usage chunks appear for claude-sonnet and gpt-5-mini (one with `finish_reason` + one pure-usage chunk); `[DONE]` follows immediately after the pure-usage chunk in all three cases.
